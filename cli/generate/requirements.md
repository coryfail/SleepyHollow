# API contracts and typed clients

## Purpose

Generate trustworthy, consumable API outputs from the same normalized route and
schema definitions used by the runtime.

## In scope

- OpenAPI specification and local API documentation.
- Framework-neutral typed TypeScript client.
- Typed requests, responses, and RFC 9457 errors.
- Configurable base URL, fetch implementation, and authentication injection.
- Staleness and supported breaking-change analysis.

## Requirements

### Normalized contract input

`hollow generate` shall consume one deterministic normalized contract inventory
from SH-F002 routes and SH-F003 request and response schemas, augmented by the
declared security, error, pagination, and service metadata already used by the
runtime. Generator-only copies of request, response, or security contracts are
invalid. Each operation shall have one stable operation ID, method, path, source
location, service ID, request locations, declared success and error responses,
authentication decision, and optional pagination metadata. Duplicate operation
IDs, duplicate method and path pairs, missing response schemas, unresolved
security schemes, or schema shapes outside the supported normalized subset shall
fail generation with source diagnostics rather than weaken output.

The normalized JSON Schema view defined by SH-F003 is authoritative. Request
contracts use the schema input view and response contracts use the schema output
view. Path, query, header, and body requiredness, media types, status codes,
Problem Details extensions, and security declarations shall be preserved exactly
in generated artifacts.

### Generated artifacts

For one application or service, generation shall produce exactly these owned
artifacts beneath its `generated/` directory:

```text
generated/
├── openapi.json
├── client.ts
├── api-docs.html
└── manifest.json
```

`openapi.json` shall be OpenAPI 3.1.1 JSON with stable operation ordering,
component names, security schemes, service metadata, and JSON Schema dialect.
It shall contain every implemented normalized route and method and no
requirements-only endpoint. Errors shall use RFC 9457 media types and schemas.
Operation security shall be empty for explicit unauthenticated behavior or name
only project-defined schemes supplied by normalized configuration; generation
shall not invent bearer tokens, cookies, API keys, or identity providers.

`api-docs.html` shall be a self-contained, local, read-only document that embeds
the generated OpenAPI JSON and renders service metadata, operations, inputs,
responses, errors, and security decisions without a production deployment,
external CDN, remote script, network request, or write-capable API console. It
shall remain usable with keyboard navigation and narrow viewports.

`manifest.json` shall use a versioned schema and record the service ID, generator
version, normalized-input digest, and SHA-256 digest of every other generated
artifact. Artifact serialization shall use UTF-8, lexicographically stable map
ordering where semantic order is irrelevant, deterministic operation and schema
ordering, two-space JSON indentation, and one final newline. No timestamp,
absolute path, random value, host detail, or ambient environment value may enter
generated bytes.

Generation shall stage the complete owned artifact set before replacing the
prior set. A failed render or write shall leave the previous set intact. The
command may replace files named by the current or previous generated manifest
but shall not overwrite or delete an unknown user file. Check mode shall perform
no writes and shall report a missing, edited, extra-owned, or stale artifact with
its path, expected digest, actual digest when available, and regeneration
guidance.

### Typed TypeScript client

OPEN-009 is resolved with one dependency-free ES module based on standard
`Request`, `Response`, `AbortSignal`, and `fetch` interfaces. `client.ts` shall
export the operation input and success types, typed RFC 9457 problem unions,
`ApiError`, `ResponseContractError`, and:

```ts
const client = createClient({
  baseUrl: "https://api.example.test",
  fetch: customFetch,
  authenticate: async ({ operationId, request }) => request,
  responseValidation: "error",
});
```

`baseUrl` is required and normalized without discarding an approved path prefix.
`fetch` defaults to `globalThis.fetch` and accepts an injected compatible
transport, including SH-F007's in-process test application. `authenticate` is an
optional operation-aware hook that receives a constructed immutable request and
returns a request; the generated client shall not store credentials, prescribe a
token or session model, or serialize secrets into generated source. Every
operation accepts an optional cancellation signal and request-header additions
without allowing callers to replace generated path, query, body, or content-type
encoding accidentally.

Each implemented operation shall be exposed as a stable named method whose input
type distinguishes path, query, header, and body values and whose success type is
discriminated by declared success status when multiple success responses exist.
A declared non-success response shall throw `ApiError` containing the HTTP
status, operation ID, response headers, and typed safe Problem Details body. An
undeclared status, invalid content type, malformed JSON, or body that violates
the generated response validator shall throw `ResponseContractError` when
`responseValidation` is `"error"`. Validation may be disabled explicitly with
`"off"`; it shall never silently coerce an invalid response into the success
type.

The generated module shall contain no Deno KV import, repository adapter,
filesystem access, environment read, service discovery, credential store, or
framework runtime dependency. A service client represents only its owning
service's HTTP contract, so cross-service use cannot grant persistence access.

### Change analysis and command behavior

Breaking-change analysis shall compare a prior generated OpenAPI document with
the current normalized contract and detect, at minimum, removed routes or
methods, newly required path/query/header/body input, removed response
properties, narrowed input or response types, changed or removed declared error
responses, stronger or incompatible authentication requirements, and changed
pagination cursor, limit, or response-envelope behavior. Each finding shall have
a stable code, severity, service and operation IDs, method and path, affected
contract element, before and after summaries, source location when resolvable,
and safe review guidance. Additive compatible changes shall be distinguished
from breaking changes.

`hollow generate` shall preview artifact and contract changes before replacing a
prior owned set and shall return nonzero for invalid normalized input or failed
atomic output. `hollow generate --check` shall return zero only when regenerated
bytes and the manifest match the current files exactly. `--json` shall expose a
versioned result containing service ID, input digest, artifact paths and digests,
staleness, breaking and additive changes, diagnostics, and whether writes
occurred. Human and JSON modes shall derive from the same normalized result.

## Acceptance criteria

- AC-F010-001: `hollow generate` produces a valid OpenAPI document containing
  every implemented route and method from the normalized route inventory.
- AC-F010-002: OpenAPI request, response, error, and security schemas match the
  runtime definitions in consistency tests.
- AC-F010-003: Local API documentation renders the generated contract without
  requiring a production deployment.
- AC-F010-004: The generated TypeScript client exposes typed inputs, success
  responses, and RFC 9457 errors for every implemented operation.
- AC-F010-005: A consumer can configure the client's base URL and fetch
  implementation.
- AC-F010-006: A consumer can inject authentication without the client requiring
  a specific identity or token model.
- AC-F010-007: Configured runtime response validation detects a server response
  that violates the generated client contract.
- AC-F010-008: Generation is deterministic for unchanged inputs and verification
  detects edited or stale generated artifacts.
- AC-F010-009: Each supported breaking-change category produces an actionable
  report naming the affected operation and contract element.
- AC-F010-010: Generated clients can represent separate service contracts without
  permitting direct access to another service's persistence.

## Out of scope

- Clients for languages other than TypeScript in the first release.
- An authentication SDK or prescribed token storage.

## Dependencies and assumptions

OPEN-009 is resolved by the dependency-free Web Standards client shape above.
SH-F002 supplies normalized route identity and metadata; SH-F003 supplies the
fail-closed runtime and JSON Schema contract views. Project-defined OpenAPI
security-scheme configuration is normalized input, not a generator-owned
authentication decision. SH-F007's compatible in-process fetch seam is available
for client tests but is not a runtime dependency of generated output.
